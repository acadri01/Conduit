# Neutral file build walkthrough

A field-by-field guide to building a `.cii` neutral file `iecho.exe` will actually accept, written
from three sources together — never just one:

1. **`reference/NeutralFile-v15.pdf`** — the vendor format spec (FORTRAN format descriptors,
   field order, field meaning).
2. **`fixtures/real-samples/*.cii`** — three real CAESAR II-exported files (`TESTv15.cii`,
   `TESTv15_slugged.cii`, `44002.cii`), committed with the user's explicit authorization as a
   narrow exception to the clean-room rule (see `reference/README.md`). These are *ground truth*:
   whatever they contain is, by construction, something `iecho.exe` and CAESAR II itself accept.
3. **Conduit's own `NeutralFileFixtureBuilder`** (`tests/Conduit.Tests/TestHelpers/`), which
   builds synthetic files from these confirmed rules — every fixture under `fixtures/` (except
   `real-samples/`) is generated by it.

**Rule for this file: never add a claim here that isn't checked against a real sample.** The vendor
PDF's prose and the real samples' actual bytes disagree in at least one confirmed place (the
ELEMENTS color/visibility line, below) — when they disagree, the real sample wins, because it's
proof of what CAESAR II's own writer/reader actually do, not just what the docs say they do.

## File-level rules

- **CRLF line endings, always.** `NeutralFileWriter` writes CRLF on every platform regardless of
  `Environment.NewLine`; `.gitattributes` pins `*.cii` to `eol=crlf` so a local `core.autocrlf`
  setting can't silently break this. Confirmed: LF-only output is rejected by `iecho.exe`.
- **Fixed-width columnar records**, not whitespace-delimited. Real-value lines are FORTRAN
  `(2X, 6G13.6)`: 2 leading spaces, then up to 6 fields of exactly 13 characters each, packed with
  no separator (a negative sign occupies the column a space would otherwise use). Integer lines
  are `(2X, 6I13)` — same 13-character field width. Never split a data line on whitespace; always
  slice by fixed column position (`FixedWidth.SliceField`).
- **20 sections, in a fixed order**: `VERSION, CONTROL, ELEMENTS, AUX_DATA, BEND, RIGID, EXPJT,
  RESTRANT, DISPLMNT, FORCMNT, UNIFORM, WIND, OFFSETS, ALLOWBLS, SIF&TEES, REDUCERS, FLANGES,
  EQUIPMNT, MISCEL_1, UNITS, COORDS`. Each starts with a `#$ <NAME>` header line. An empty section
  is still present as a bare header with zero data lines — never omit a header.

## `#$ VERSION`

61 lines total: one info line (`5.00000  15.0000  1252` — CAESAR II version/build/codepage,
confirmed identical across all real samples and safe to reuse verbatim), then exactly 60 title-page
lines, FORTRAN `(2X, A75)` — 75-char fields, left-justified, space-padded, blank in every real
sample and Conduit's own fixtures alike except the last, which the fixture builder uses for a
provenance note. **Gotcha already fixed**: an earlier version of the fixture builder wrote only the
info line with zero title lines, silently shifting every subsequent section's line numbers by 60 —
a strong candidate for any `iecho.exe` "line # NN" error where NN looks like it's ~60 lines short of
where the real problem is.

## `#$ CONTROL`

One fixed 19-value record (3 lines of 6 + 1 line of 1), all integers, `(2X, 6I13)`: counts of
elements, nozzles, hangers, node names, reducers, flanges, bends, rigids, expansion joints,
restraints, displacements, force/moments, uniform loads, wind loads, offsets, allowable-stress
records, intersections, `IZUP` (0 = Y-up, 1 = Z-up), equipment checks. These counts **must** match
the actual record count in each corresponding section exactly — `NeutralFile.AddRestraint` keeps
`NumRestraints` in sync for that reason; any manual section edit needs the same care.

## `#$ ELEMENTS`

The section most worth double-checking field-by-field, since a single wrong line here breaks
`iecho.exe`'s parse partway through the file with a misleadingly-late line number. Each element is
a fixed **15-line record**:

| Lines | Content | Format |
|---|---|---|
| 1–9 | 53 real values (below) | `(2X, 6G13.6)`, 6 per line (last line has 5) |
| 10 | Element name, length-prefixed | `(7X, I5, 1X, A500)` |
| 11 | Line number, length-prefixed | `(7X, I5, 1X, A500)` |
| 12 | Line color, line visibility | **see gotcha below** |
| 13–15 | 15 auxiliary-data pointers (IEL array) | `(2X, 6I13)`, 6+6+3 |

**The 53 real values, in order** (0-based index in `Element.RealValues`): FROM node (0), TO node
(1), DeltaX/Y/Z (2–4), outside diameter (5), wall thickness (6), insulation thickness (7),
corrosion allowance (8), thermal expansion coefficients #1–9 (9–17), pressures #1–9 (18–26),
elastic modulus cold (27), Poisson's ratio (28), **pipe density (29)**, insulation density (30),
fluid density (31), minus/plus mill tolerance (32–33), seam weld flag (34), hydro pressure (35),
elastic modulus hot #1–9 (36–44), "wL" factor (45), element orientation angles (46–47), cladding
thickness/density (48–49), insulation+cladding weight/length (50), refractory thickness/density
(51–52). Unspecified reals default to `0.0` — confirmed real samples routinely leave pipe density,
elastic modulus, and Poisson's ratio at `0.0` (material data isn't always baked into the neutral
file itself), so `SpanLimitCalculator` must never assume these are populated.

**Name/line-number lines**: `(7X, I5, 1X, A500)` — 7 spaces, the string's length right-justified in
5 chars, 1 space, then the string itself (so a length of 0 is a valid, legal value — confirmed: some
elements in `TESTv15.cii` have both empty). **Do not** assume a non-empty name/line-number is
required; it isn't.

**Gotcha (confirmed cause of a real `iecho.exe` rejection — "Error processing ELEMENT section, line
# NN")**: `NeutralFile-v15.pdf` labels line 12 "Line Color and Line Visibility, using the format
(2X, 6G13.6)" — i.e. real-value/scientific-notation format, same as the 53-value block. **All 3
real samples disagree**: this line is written as two plain 13-character-wide integers, byte-for-byte
`             -1           -1` (no decimal point, no `E` exponent) — confirmed identical across
every element in all 3 real samples (49 elements checked). Conduit's fixture builder originally
wrote this line with `FixedWidth.FormatRealLines` (producing `0.000000E+00-1.000000E+00`), which
`iecho.exe` rejected. Fixed to use `FixedWidth.FormatIntLines([-1, -1])` instead —
`ElementSectionFormatTests` asserts this byte-for-byte against the real samples so it can't
regress silently. **When the vendor doc and a real sample disagree, trust the real sample.**

**The 15 auxiliary pointers (IEL array)**, in order: bend, rigid element, expansion joint,
restraint, displacement, force/moment, uniform load, wind load, element offset, allowable stress,
intersection, node name, reducer, flange, nozzle/equipment check. Each is a 1-based pointer into
that auxiliary section's records for this element, or `0` for "none" — `0` is common and legal
(most elements reference only a handful of these).

## `#$ UNITS`

4 lines of 22 real conversion constants (`(2X, 6G13.6)`), then 24 lines of unit labels
(`(2X, A<n>)`). The first constant, **CNVLEN**, is "how many native length units equal one inch" —
confirmed `25.4` in every real sample (mm-native: 25.4 mm = 1 inch) — an English-native file would
read `1.0` (1 inch = 1 inch) instead, though Conduit hasn't seen a real English-unit sample to
confirm byte-for-byte. `UnitsSection.Parse` reads only this one constant and derives
`LengthToMillimetres = 25.4 / CNVLEN`; a missing/unparseable `#$ UNITS` block defaults to metric
(`CNVLEN = 25.4` equivalent), per direct instruction — Conduit's default unit system is
millimetres, and every span/weight/stress calculation converts a non-metric file's data to
mm/N/MPa/kg before computing (see `SpanLimitCalculator`'s doc comment; QUESTIONS.md's "mm as
default" entry). Never empty in a real file, even when all values are the generic defaults — like
`#$ WIND`, this looks like a CAESAR II structural requirement, not optional per-project data.

## `#$ WIND`, `#$ COORDS`

`#$ WIND` is never truly empty even with no wind load applied — confirmed byte-identical
(`0.0 0.7 0.0 0.0 0.0 0.0`) across all real samples and Conduit's own default. `#$ COORDS` lists the
start coordinate of each *discontinuous* piping segment; a file whose elements form one contiguous
chain per run has nothing to list beyond the zero count line — confirmed against real samples.

## Sections not yet used by Conduit's logic

`#$ AUX_DATA`, `#$ BEND`, `#$ RIGID`, `#$ EXPJT`, `#$ DISPLMNT`, `#$ FORCMNT`, `#$ UNIFORM`,
`#$ OFFSETS`, `#$ SIF&TEES`, `#$ REDUCERS`, `#$ FLANGES` — Conduit reads these as opaque raw lines
and writes them back verbatim (never regenerates or interprets them). `#$ RESTRANT`,
`#$ ALLOWBLS`, `#$ EQUIPMNT`, and `#$ MISCEL_1`'s RRMAT array are the only auxiliary sections
Conduit's own model parses — see their respective `NeutralFiles/*.cs` classes.

## Known open items (not yet built)

- **CNODES**: a CAESAR II connection-point concept (reading forces/moments between elements at a
  shared node) — a CNODE-bearing node is explicitly *not* an anchor support and must be excluded
  from future support-placement candidate logic. Not yet researched in the neutral-file format
  itself (which section/field carries the CNODE number) — logged in QUESTIONS.md, not yet
  implemented.
- **Zero-weight rigid equipment** (per `44002.cii`'s note): elements modeling equipment as rigid
  with no weight should be ignored for support-placement purposes. Not yet implemented — logged in
  QUESTIONS.md, pending its own support-placement-logic consultation turn per CLAUDE.md.

## How to verify a change against this walkthrough

1. Never trust a paraphrase (including this document) over the primary sources — re-check
   `reference/NeutralFile-v15.pdf` and, for anything the vendor doc is ambiguous or silent about,
   the real bytes in `fixtures/real-samples/*.cii` directly (`cat -A`, `od -c`, or a throwaway
   scratch test reading the file via `NeutralFileReader` and dumping field values — see
   `TESTING.md`).
2. Any structural change to how Conduit *writes* a section belongs in
   `NeutralFileFixtureBuilder` (tests/fixtures only — `NeutralFileWriter` never regenerates
   `#$ ELEMENTS` from the model, it writes the section's raw lines back verbatim, per
   `Element.cs`'s doc comment) or, for the sections Conduit actually reads and modifies
   (`RESTRANT`, `CONTROL`), in `NeutralFileWriter` itself.
3. Add or extend a regression test in `tests/Conduit.Tests/NeutralFiles/` asserting the exact byte
   layout, not just that the file round-trips or parses without throwing — a format bug can easily
   parse fine on Conduit's own (more permissive) reader while still failing `iecho.exe`'s stricter
   one, which is exactly how the color/visibility bug above shipped unnoticed the first time.
4. Regenerate any committed fixture that used the changed code path (see TESTING.md's "Adding or
   changing a fixture"), and if a real CAESAR II license/install is available, actually run
   `iecho.exe` against the result — Conduit's own reader accepting a file is necessary but not
   sufficient proof it's correct.
